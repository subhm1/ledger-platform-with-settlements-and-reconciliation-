
# Accounting Domain Model

**Project:** Ledger Platform  
**Phase:** 1 — Accounting Domain and Data Model  
**Status:** Approved for schema design

## 1. Purpose and Scope

This document defines the accounting model, transaction rules, account lifecycle, reversal policy, and integrity requirements for the initial version of the Ledger Platform.

PostgreSQL is the authoritative source of financial records. The initial version supports single-currency double-entry accounting. Foreign exchange, partial reversals, drafts, and cached account balances are out of scope.

## 2. Core Domain Entities

### 2.1 Currency

Represents a supported currency.

- `code`: uppercase ISO 4217 currency code.
- `minor_unit_exponent`: number of decimal places used by the currency.
- `enabled`: whether the currency can be used for new postings.

Currency precision must not be changed in a way that silently reinterprets historical amounts.

Once a currency is referenced by financial records, its precision must remain unchanged. Disabling a currency prevents new postings without affecting historical records.

### 2.2 Account

Represents an accounting account, not a user-facing wallet interface.

- `id`: internal UUID identifier generated by PostgreSQL.
- `account_code`: unique account reference.
- `account_class`: `ASSET`, `LIABILITY`, `EQUITY`, `REVENUE`, or `EXPENSE`.
- `account_role`: constrained business-purpose classification.
- `currency_code`: the account's single currency.
- `status`: `ACTIVE`, `SUSPENDED`, or `CLOSED`.
- `created_at`: creation timestamp.

The initial supported account roles are:

- `CUSTOMER_WALLET`: customer wallet balances owed by the platform.
- `MERCHANT_PAYABLE`: amounts owed to merchants.
- `SETTLEMENT_CASH`: cash or funds held for settlement purposes.
- `BANK_CLEARING`: amounts passing through bank-clearing operations.
- `FEE_REVENUE`: revenue earned from fees.
- `PLATFORM_EXPENSE`: expenses incurred by the platform.
- `SUSPENSE`: amounts awaiting investigation or classification.

Account roles and accounting classes are separate concepts. Both must be validated by database constraints.

The initial implementation uses a fixed database `CHECK` constraint for supported account roles. Adding a new role requires a reviewed schema migration.

Each account belongs to exactly one currency. Its accounting class determines its normal balance.

### 2.3 Journal Transaction

Represents one complete financial event.

- `id`: internal UUID identifier generated by PostgreSQL.
- `transaction_reference`: unique transaction reference.
- `currency_code`: transaction currency.
- `description`: explanation of the financial event.
- `created_at`: creation timestamp.
- `posted_at`: posting timestamp.
- `reversal_of_transaction_id`: reference to the original transaction when this transaction is a reversal.

The initial version persists only successfully posted journal transactions. Draft transactions are out of scope. A failed posting must not leave partial financial records.

### 2.4 Journal Entry

Represents one debit or credit against an account.

- `id`: internal UUID identifier generated by PostgreSQL.
- `transaction_id`: parent journal transaction.
- `account_id`: affected account.
- `currency_code`: currency of the journal transaction.
- `direction`: `DEBIT` or `CREDIT`.
- `amount_minor`: positive integer amount in minor units.
- `created_at`: creation timestamp.

Every entry belongs to one transaction and one account. The account currency must match the transaction currency.

### 2.5 Idempotency Record

Prevents repeated requests from producing duplicate financial effects.

- `id`: internal UUID identifier generated by PostgreSQL.
- `scope`: identity of the caller or merchant within which the key is unique.
- `idempotency_key`: client-supplied request key.
- `request_fingerprint`: identifies the request parameters relevant to the financial operation.
- `transaction_id`: resulting journal transaction.
- `created_at`: creation timestamp.

The idempotency record and financial effect must be committed atomically. Reusing a key with the same request returns the existing result. Reusing it with a different request is rejected.

### 2.6 Reversal Audit

Records explicitly authorized reversals involving suspended or closed accounts.

- `id`: internal UUID identifier generated by PostgreSQL.
- `original_transaction_id`: transaction being reversed.
- `reversal_transaction_id`: compensating transaction.
- `authorized_by`: authenticated actor authorizing the exception.
- `reason`: non-empty explanation for the exception.
- `created_at`: authorization and audit timestamp.

The reversal audit record must be created atomically with the corresponding reversal. The application role must not be allowed to modify or delete audit records.

## 3. Accounting Classes and Normal Balances

| Account class | Normal balance | Increases with |
|---|---|---|
| ASSET | Debit | Debit |
| EXPENSE | Debit | Debit |
| LIABILITY | Credit | Credit |
| EQUITY | Credit | Credit |
| REVENUE | Credit | Credit |

The accounting class is distinct from the business role. For example, a customer wallet is normally a liability account because the platform owes the wallet balance to its customer.

Contra accounts and exceptional account-class behavior are out of scope for the initial version.

## 4. Money and Currency Rules

- Store entry amounts as positive `BIGINT` values in minor units.
- Reject zero and negative entry amounts.
- Never use floating-point types for financial amounts.
- Store currency precision explicitly rather than assuming every currency has two decimal places.
- Each account and each journal transaction uses exactly one currency.
- Every entry's account currency must equal its transaction currency.
- Foreign-exchange transactions are out of scope.
- Aggregate debit and credit calculations must avoid unsafe integer overflow.
- Currency precision must not be changed after financial records reference that currency.
- Disabling a currency must not alter historical financial records.

Example: INR 125.50 is stored as 12,550 minor units when the currency exponent is 2.

## 5. Double-Entry Invariants

Every successfully posted journal transaction must satisfy all of the following:

1. It contains at least two journal entries.
2. Total debits equal total credits.
3. Every entry has a positive amount and a valid direction.
4. Every referenced account and transaction exists.
5. Every entry's account currency matches the transaction currency.
6. All ordinary postings satisfy the account lifecycle policy.
7. All entries and the transaction are persisted atomically.

A balanced transaction may contain more than two entries. Debit and credit equality is required for each transaction, not merely across the entire ledger.

## 6. Account Lifecycle

### ACTIVE

Permitted to participate in ordinary postings, subject to all other validation rules.

### SUSPENDED

Blocked from ordinary postings. A compensating reversal may affect a suspended account only through the explicitly authorized reversal workflow.

### CLOSED

Permanently blocked from ordinary postings. A compensating reversal may affect a closed account only through the explicitly authorized correction workflow. Reversal processing must not reopen the account.

Account status must be checked safely under concurrent operations. Application validation alone is insufficient if another transaction can change the account status before posting completes.

## 7. Posting and Transaction Lifecycle

- Only successfully posted transactions are persisted in the initial version.
- Posting is atomic: all financial effects commit together, or none do.
- A failed posting must not leave partially committed entries.
- Posted transactions and their entries are immutable.
- Posted entries must never be edited or deleted to correct a financial error.
- Corrections are represented by new compensating transactions.
- PostgreSQL is the authoritative source for financial records.

## 8. Reversal Policy

- A reversal is a new journal transaction referencing the original posted transaction.
- The original transaction and its entries remain unchanged.
- A full reversal compensates for every original entry with the opposite debit or credit direction and the same amount and account.
- The reversal uses the original transaction's currency.
- A transaction can have at most one full reversal in the initial version.
- Partial reversals are out of scope.
- A reversal cannot itself be reversed in the initial version; a separate adjustment workflow must be designed for that situation.
- Duplicate reversal requests must not produce duplicate financial effects.
- Reversals involving suspended or closed accounts require an explicit, auditable exception path.
- Reversal validation must prevent unrelated or fabricated transactions from being treated as legitimate reversals.
- An exceptional reversal requires an authenticated authorizing actor and a non-empty reason.
- Reversal authorization and the reversal's financial effects must be committed atomically.

## 9. Balance Calculation

Account balances are derived from posted journal entries in the initial version.

For accounts with a debit normal balance:

**Balance = total debits - total credits**

For accounts with a credit normal balance:

**Balance = total credits - total debits**

Balances are calculated using the account's accounting class. Cached or materialized balances are deferred until a demonstrated performance need justifies the additional consistency requirements.

## 10. Idempotency and Uniqueness

- Every externally initiated posting request must use an idempotency key.
- Key uniqueness is scoped to the relevant caller or merchant.
- A database uniqueness constraint prevents duplicate keys within the defined scope.
- The request fingerprint detects reuse of a key with different request parameters.
- Idempotency handling and the financial posting must be atomic.
- Concurrent retries using the same key must not create duplicate financial effects.
- Internal identifiers, transaction references, and required business references must have explicit uniqueness rules.
- A retry with the same key and fingerprint returns the original successful result.
- A retry with the same key but a different fingerprint is rejected.

## 11. Integrity Enforcement Strategy

| Invariant | Enforcement mechanism |
|---|---|
| Valid entry amount | PostgreSQL `CHECK` constraint requiring `amount_minor > 0` |
| Valid entry direction | PostgreSQL `CHECK` constraint restricting values to `DEBIT` or `CREDIT` |
| Valid account class | PostgreSQL `CHECK` constraint |
| Valid account role | PostgreSQL `CHECK` constraint with the approved role set |
| Valid account status | PostgreSQL `CHECK` constraint |
| Referenced records exist | Foreign keys |
| Unique account and transaction references | Unique constraints |
| Account currency matches transaction currency | Composite foreign keys using the currency code on each journal entry |
| Minimum two entries per transaction | Posting function validates the complete transaction before returning; the caller commits atomically |
| Equal debits and credits | Posting function validates aggregate debits and credits before commit |
| Account status rules | Posting function locks affected account rows and validates status |
| Posted-record immutability | Database triggers and restricted write permissions |
| At most one full reversal | Unique constraint or partial unique index on `reversal_of_transaction_id` for reversal transactions |
| Reversal matches original entries | Posting function verifies that every original entry is compensated by an opposite-direction entry for the same account, currency, and amount |
| Reversal targets an eligible transaction | Posting function verifies that the original exists, is posted, and is not itself a reversal |
| Idempotency | Unique constraint on the idempotency scope and key, combined with atomic posting |
| No partial posting | PostgreSQL transaction boundaries and rollback |
| Currency precision protection | Database permissions and controlled currency-management operations |
| Reversal exception audit | Foreign keys, uniqueness constraints, restricted write permissions, and atomic posting |

### 11.1 Controlled Posting Mechanism

The application must not be allowed to bypass critical accounting validation through direct writes.

- A database posting function validates the complete transaction before it becomes a committed financial record.
- The function validates entry count, debit/credit equality, currency consistency, account status, and reversal rules.
- The function executes within the caller's database transaction. Any validation failure aborts the posting operation.
- Application database permissions must prevent direct writes that bypass the controlled posting path.
- Database triggers and constraints provide additional protection for immutable records and row-level invariants.
- The function must handle idempotency consistently with the financial posting operation.
- Account rows must be locked in a consistent order to reduce deadlock risk during concurrent postings.

The posting function accepts a complete posting request, creates the transaction and entries, validates all invariants, and returns only if validation succeeds. The function does not commit independently; the caller's PostgreSQL transaction commits all changes atomically.

The application database role receives `EXECUTE` permission for the posting function but no direct `INSERT`, `UPDATE`, or `DELETE` permission on ledger tables. The function owner is a separate non-login role. If `SECURITY DEFINER` is used, the function must set a fixed, safe `search_path`.

The exact SQL signature and DDL are implementation details for the schema implementation step. Tests must cover direct-write denial, concurrent posting, and rollback after validation failure.

### 11.2 Currency Consistency

Each journal entry carries the transaction currency code. Composite foreign keys reference both the account identifier and currency code, and both the transaction identifier and currency code.

This ensures that an entry cannot reference an account or transaction with a different currency.

Currency metadata must be managed so that the minor-unit exponent cannot be changed after the currency has been referenced by financial records.

### 11.3 Reversal Integrity

A full reversal must compensate for every original entry with the same account and amount but the opposite direction.

- The original transaction must exist and must not itself be a reversal.
- A unique constraint prevents multiple full reversals of the same original transaction.
- Reversal validation must run inside the controlled posting mechanism.
- Account-status exceptions must be restricted to authorized reversals and recorded in an audit trail.
- The reversal must use the original transaction's currency.
- The reversal must contain the exact compensating entries, without omitted or additional entries.

Ordinary row-level `CHECK` constraints cannot validate aggregate sums or compare entries across transactions. These rules require controlled database-level validation.

### 11.4 Reversal Exception Audit

Every authorized reversal involving a suspended or closed account must record the authorizing actor, reason, original transaction, reversal transaction, and timestamp.

The schema must provide an auditable record for this exception. Authorization must not be inferred solely from the account status or the fact that a request is labeled as a reversal.

The reversal and its audit record must be committed atomically. The ordinary application role must not be allowed to alter or delete the audit record.

## 12. Initial Version Boundaries

The initial version does not include:

- Multi-currency journal transactions or foreign exchange.
- Draft journal transactions.
- Partial reversals.
- Reversal of a reversal.
- Cached account balances.
- Contra accounts.
- Distributed services or additional infrastructure without a demonstrated need.

Settlement and reconciliation will be built on top of the ledger's reliable financial records in later phases.

## 13. Implementation Gate

The following Phase 1 design decisions are finalized:

- The initial account classes are `ASSET`, `LIABILITY`, `EQUITY`, `REVENUE`, and `EXPENSE`.
- The initial account roles are `CUSTOMER_WALLET`, `MERCHANT_PAYABLE`, `SETTLEMENT_CASH`, `BANK_CLEARING`, `FEE_REVENUE`, `PLATFORM_EXPENSE`, and `SUSPENSE`.
- Account roles and classes are separate and constrained by the database.
- Account status is restricted to `ACTIVE`, `SUSPENDED`, or `CLOSED`.
- Currency and account constraints must preserve historical financial meaning.
- Transaction and entry relationships must enforce currency consistency.
- The controlled PostgreSQL posting function enforces balancing and posting invariants.
- Account-status locking and authorized reversal exceptions are required.
- Idempotency is scoped and enforced by database uniqueness.
- Posted-record immutability is enforced at the database level.
- Integration tests must cover valid postings, invalid postings, reversals, retries, concurrency, and rollback.
- Database permissions must prevent direct financial writes that bypass the posting function.

The database schema will be introduced in a new Flyway migration named `V2__create_accounting_schema.sql`. Previously applied migrations must not be modified.

The schema must be reviewed before the migration is created or applied.
