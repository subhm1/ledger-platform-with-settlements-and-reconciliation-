# Provider Payments: scope, states, and accounting gate

## 1. Scope

`/payments` remains the simulated internal-wallet transfer page. It can move INR between the five demo wallets and posts a balanced ledger transaction. It does not call Razorpay.

`/provider-payments` is a separate operator page for **Razorpay Test Mode customer-to-platform collections**. Checkout collects a payment **to the platform merchant account**. It does not pay Swati, Shreya, Arnav, Ashwin, or Shubham, does not debit a customer bank account in live mode, and does not create a payout.

This application never collects card, UPI, or other payment-method data. Razorpay Checkout owns method entry. Stored fields are request identity, amounts in integer paise, INR, purpose, business reference, provider order/payment IDs, lifecycle state, timestamps, and short safe diagnostic codes/details.

## 2. Data the demo collects and displays

**Collected by the operator form**

- Amount in INR, converted to integer paise (`amount_minor`)
- Purpose (1–100 characters)
- Business reference (1–150 characters)
- Idempotency key (header; generated by the UI and reused for an unchanged retry)

**Created by the backend**

- Internal attempt ID and unique `receipt` (`lp_` + compact UUID)
- Provider order ID after a verified Razorpay order
- Provider payment ID after verified Checkout or webhook evidence
- State, version, timestamps, append-only event history

**Displayed**

- Amount, currency, reference, state, provider IDs, created/updated time
- Accounting gate (`ACCOUNTING_GATE_PENDING` only after `CAPTURED_VERIFIED`, otherwise `NOT_CAPTURED`)
- Timeline of safe events (no raw provider payloads, no secrets, no card data)

## 3. Payment states and allowed transitions

Attempts insert only as `ORDER_PENDING` with no provider IDs.

| From | To |
| --- | --- |
| `ORDER_PENDING` | `READY_FOR_CHECKOUT`, `ORDER_UNKNOWN`, `REVIEW_REQUIRED` |
| `ORDER_UNKNOWN` | `READY_FOR_CHECKOUT` (recovered unused order with matching receipt/amount/currency), `REVIEW_REQUIRED` |
| `READY_FOR_CHECKOUT` | `PAYMENT_PENDING`, `AUTHORIZED`, `CAPTURED_VERIFIED`, `FAILED`, `REVIEW_REQUIRED` |
| `PAYMENT_PENDING` | `AUTHORIZED`, `CAPTURED_VERIFIED`, `FAILED`, `REVIEW_REQUIRED` |
| `AUTHORIZED` | `PAYMENT_PENDING`, `CAPTURED_VERIFIED`, `FAILED`, `REVIEW_REQUIRED` |
| `FAILED` | `PAYMENT_PENDING`, `AUTHORIZED`, `CAPTURED_VERIFIED`, `REVIEW_REQUIRED` |
| `CAPTURED_VERIFIED` | `REVIEW_REQUIRED` only (conflicts after capture; never silently recede to failed) |
| `REVIEW_REQUIRED` | `PAYMENT_PENDING`, `AUTHORIZED`, `CAPTURED_VERIFIED`, `FAILED`, `READY_FOR_CHECKOUT` when later verified evidence supports it |

Meaning:

- `ORDER_PENDING`: local idempotent request recorded; Razorpay create-order not finished.
- `READY_FOR_CHECKOUT`: backend saved and validated a Razorpay order. Checkout is allowed only in this state, and only with a `rzp_test_` key ID.
- `ORDER_UNKNOWN`: create-order timed out or otherwise ambiguous. The UI must not create another order. Recovery looks up the unique local receipt.
- `PAYMENT_PENDING` / `AUTHORIZED`: checkout happened or the provider reports authorization; capture is not confirmed.
- `CAPTURED_VERIFIED`: server-side Checkout signature **or** verified webhook, **plus** current Razorpay order/payment records, confirm capture. Displayed accounting state is `ACCOUNTING_GATE_PENDING`.
- `FAILED`: provider reports failure with unpaid order amounts.
- `REVIEW_REQUIRED`: identity, amount, currency, receipt, or status checks failed, or later evidence conflicts with a capture.

Request identity (amount, currency, purpose, reference, receipt, idempotency) is immutable. Provider order/payment IDs cannot be replaced once set.

## 4. Accounting gate (approved decision for this phase)

**No journal posting, wallet credit, refund, or payout is performed for provider payments in this phase.**

Captured Test Mode money is evidence that Razorpay reported a paid order. It is not a ledger transaction until an accounting owner approves:

- the exact debit account (expected: settlement/cash or provider clearing asset)
- the exact credit account (expected: platform/customer liability or unearned collection liability)
- the posting trigger (`CAPTURED_VERIFIED` vs settlement-report match)
- fee, tax, and failure/refund treatment

Until that approval, `CAPTURED_VERIFIED` remains `ACCOUNTING_GATE_PENDING`. Reconciliation (plan step 6) is a later mapping of provider payments, ledger postings, and settlement files. Browser Checkout callbacks never mark success by themselves.

## 5. Backend verification rules

- Operator APIs use the signed frontend session and server-held Basic credentials.
- Razorpay key ID, API secret, and webhook secret stay on the backend. Checkout receives only `rzp_test_` key ID, order ID, amount, and currency.
- Checkout signatures are HMAC-SHA256 of `orderId|paymentId` using the API secret.
- Webhooks are authenticated by HMAC-SHA256 of the **raw request body** using the webhook secret (`X-Razorpay-Signature`). The webhook route is not operator-basic-auth; invalid signatures are rejected and not stored.
- After a verified Checkout or webhook signal, the backend fetches the current order and payment from Razorpay before changing attempt state.
- Duplicate webhook event IDs are unique per provider/environment. Already-processed events are acknowledged without re-applying. Delayed events use current provider records. A failed/conflicted event after `CAPTURED_VERIFIED` moves the attempt to `REVIEW_REQUIRED`.
- Timeouts on create-order become `ORDER_UNKNOWN`. Recovery must not create a second order.
- Provider error bodies are never returned to the UI. Card data is never stored.

## 6. Operational boundary

Create forward-only migrations only. Do not apply them to the persistent review database without a separate migration approval. Do not claim sandbox connectivity until a real Test Mode request is made. Public/live deployment stays deferred (plan step 7).
